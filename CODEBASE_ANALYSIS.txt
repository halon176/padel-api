1. OVERALL ARCHITECTURE
================================================================================

Application Flow:
  run.py → config.py (loads settings) → main.py (FastAPI app)
    ↓
  Database initialization (creates SQLite tables on startup)
    ↓
  Router registration (users, availabilities, reservations)
    ↓
  Uvicorn server starts on configured port (default 8000)

Design Pattern:
  - Routers: Handle HTTP requests/responses
  - Controllers: Database operations
  - Schemas: Pydantic models for request/response validation
  - Models: SQLAlchemy ORM definitions
  - Security: JWT-based authentication
  - Utils: External service integrations (email notifications)

Database-First Initialization:
  main.py calls: Base.metadata.create_all(bind=engine)
  This creates all tables on application startup if they don't exist

3. DATABASE MODELS & RELATIONSHIPS
================================================================================

Tables & Relationships:
  
  users
  ├─ id (PK)
  ├─ username (UNIQUE)
  ├─ email (UNIQUE)
  ├─ password (hashed with bcrypt)
  ├─ is_active (default: True)
  ├─ created_at (auto timestamp)
  ├─ availabilities (1-to-many with Availability)
  └─ reservations (many-to-many via reservation_relations)
  
  availabilities
  ├─ id (PK)
  ├─ user_id (FK to users, cascade delete)
  ├─ start (datetime)
  ├─ end (datetime)
  ├─ created_at (auto timestamp)
  └─ UNIQUE(user_id, start, end) - prevents duplicate bookings
  
  reservations
  ├─ id (PK)
  ├─ start (datetime)
  ├─ end (datetime)
  ├─ created_at (auto timestamp)
  ├─ users (many-to-many via reservation_relations)
  └─ UNIQUE(start, end) - one reservation per time slot
  
  reservation_relations (join table)
  ├─ user_id (FK to users, cascade delete/update)
  ├─ reservation_id (FK to reservations, cascade delete/update)
  └─ PRIMARY KEY(user_id, reservation_id)

Constraints:
  - Foreign key cascading: ON DELETE CASCADE, ON UPDATE CASCADE
  - Unique constraints enforce business rules
  - SQLite: check_same_thread=False (threading issue)

4. AUTHENTICATION & SECURITY
================================================================================

Authentication Method:
  - JWT (JSON Web Tokens) with Bearer scheme
  - Algorithm: HS256 (HMAC with SHA-256)
  - Expiration: Configurable (default: 60 minutes)

Implementation:
  
  JWT Generation (sign_jwt):
    - Includes user_id and exp (expiration) in payload
    - Signed with SECRET_KEY
    - Returned as access_token in JSON
  
  JWT Validation (decode_jwt):
    - Verifies signature and expiration
    - Handles ExpiredSignatureError (403)
    - Handles InvalidTokenError (403)
    - Returns decoded payload
  
  Bearer Implementation (JWTBearer class):
    - Custom HTTPBearer implementation
    - Extracts token from Authorization header
    - Validates Bearer scheme
    - Returns user_id to route handlers
    - Used via Depends(JWTBearer())

Password Security:
  - Uses passlib with bcrypt hashing
  - CryptContext configured with schemes=["bcrypt"]
  - Password stored as hashed value in database
  - check_password() method for verification
  - Password not readable via property getter (raises AttributeError)

BUSINESS LOGIC ANALYSIS
================================================================================

Availability Management:
  - Users create 1-hour availability slots
  - Date must be in future (FutureDate validator)
  - Hour must be 9-22 (business hours)
  - Unique constraint: (user_id, start, end)
  - Prevents double-booking by same user

Reservation Creation Logic (4-Player Match):
  When availability is created:
    1. Check if reservation exists for this slot → reject if yes
    2. Check if user already available for this slot → reject if yes
    3. Create availability record
    4. Count total availabilities for this slot
    5. IF count >= 4:
       a. Create Reservation record
       b. Create reservation_relations for each user
       c. Send email notifications (background task)
    6. Return the created availability

Issues with Logic:

1. RACE CONDITION
   Problem: Between checking count and creating reservation
   Scenario: 
     - User A creates availability (count=3)
     - User B creates availability simultaneously (count=3)
     - User C creates availability simultaneously (count=3)
